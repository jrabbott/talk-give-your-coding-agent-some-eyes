Giving AI coding agents the signals they need to write high-quality code

D’oh! My Coding Agent Has No Eyes

Jon Abbott

Open with the Homer moment promise: this talk is a realisation story, not a config tutorial. Quality bar already existed — the agents just couldn’t see it.

I’ve outsourced most of my coding

  • Gemini CLI, GitHub Copilot, Cursor
  • SpecKit / SDD and native plan modes
  • Different models, different harnesses
  • And the output is… surprisingly good
Set the scene. This is not an “AI agents are bad” talk. Agents do nearly all the coding; results are generally great.

But… nits

  • IDE warnings and amber squiggles
  • Style drift and small code smells
  • Patterns that don’t fit the codebase
  • If my IDE is showing amber, I’m not happy
Not bugs. Not disasters. Nits. High quality bar: no amber, no warnings, no squiggles.

Something felt… different

  • Work with someone long enough and you learn their style
  • Quirks, strengths, how much detail they need
  • You develop a working relationship
Human analogy: prolonged collaboration builds intuition about how someone codes and how to review them.

Agents didn’t feel like teammates

Human teammate

You get used to

  • One person’s style
  • Predictable quirks
  • A working relationship
Agents

Every run can shift

  • Model and harness
  • Context and plan
  • Lots of teammates
Non-deterministic by nature. Common nits, but not one person you learn over time — a revolving cast.

D’OH!

Pause. Let the black slide land. Homer Simpson moment.

The agents don’t use an IDE.
They don’t have eyes.

Centrepiece. I was expecting the agent to respond to a signal it couldn’t see.
Human: sees code → sees squiggle → understands → fixes. Agent: sees code → ??? → no signal.
Your IDE is part of the feedback loop. The agent has blind spots where the human has peripheral vision.

So how do we give the agent the signal?

I didn’t need to teach the agent my preferences. I needed to make my preferences executable.

Make preferences executable

  • .editorconfig
  • Directory.Build.props / Directory.Build.targets
  • CodeMetricsConfig.txt
  • These aren’t just config files. They’re signals.
Reveal the answer after the realisation. Config as feedback channel, not as a preference document.

From tribal knowledge to rules

Human team

Knowledge lives in

  • “We generally don’t do that”
  • “The IDE will warn you”
  • People
Agent

Knowledge needs to live in

  • Build and analyzers
  • Metrics and style rules
  • Artifacts
Move the quality bar from people’s heads into the build.

.editorconfig

  • Naming, whitespace, language conventions
  • Analyzer severity and style rules
  • Don’t tell the agent what good looks like — give the toolchain a way to tell the agent
Not just formatting. Consistency becomes observable.
Directory.Build.props and Directory.Build.targets: instead of “please remember to…”, the build will tell you. Now the agent has eyes — a feedback channel.

CodeMetricsConfig.txt

  • Quality isn’t only “does it compile?”
  • Complexity, maintainability, coupling, size
  • The compiler says valid. Metrics can say getting ugly.
Encode maintainability instincts that otherwise live in your head.

An observable quality function

  • Tests — does it work?
  • Compiler — is it valid?
  • Analyzers — does it follow these rules?
  • Metrics — is it hard to maintain?
  • .editorconfig — what does consistency look like here?
Together they create an observable quality function — different questions, one feedback surface.

Agents don’t learn like teammates

Human team
  • Teach
  • Feedback
  • Learn
  • Trust
Agentic development
  • Specify
  • Signal
  • Detect
  • Correct
Soften carefully: agents don’t learn from our working relationship the way a human teammate does. New context, model, session, task — you can’t rely on a persistent relationship to carry the bar.

Don’t make the agent remember your quality bar. Make the repository remember it.

Thesis slide. The repo becomes institutional memory — not the model, not the prompt, not you.
Flip the earlier observation: the codebase becomes the consistent teammate across every agent — opinions, boundaries, feedback.
It doesn’t matter which agent I use. The agent is replaceable. The quality bar isn’t.

What I changed

Before
  • Prompt → agent → code
  • Human review
  • “Why is there a warning?”
After
  • Build + analyzers + metrics
  • Agent sees diagnostics and fixes
  • Human reviews design
The human moves up the abstraction level. Nits get caught by the system; review focuses on design.

The result

  • Agents didn’t suddenly become better programmers
  • They became better informed programmers
  • The quality bar was already there — it just wasn’t exposed
Don’t claim perfection. The trick isn’t making the agent smarter — it’s making the environment more observable. Instructions tell an agent what you want. Signals tell an agent what happened.

AI coding agents don’t have eyes.
Give them signals.
